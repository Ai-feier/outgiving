# 决策记录

一个决策一份文件。**决策记录**保存的是一次取舍的**原因**、**权衡**与**落选方案**——代码和普通文档承载不了这些，这里是它们唯一的去处。

边界：项目事实、结构、命名 → [`system/`](../../system/)；必须遵守的约束 → [`.pi/rules/`](../../.pi/rules/)；方法 → [`.pi/skills/`](../../.pi/skills/)。本目录只放长期决策。

## 布局与命名

路径编码状态与主题：`{lifecycle}/<YYYY-MM-DD>-<slug>.md`。

- **`proposed/`** —— 评审后尚未实施。
- **`implemented/`** —— 决策已落地。文件描述「决定了什么、否决了什么」，并随已落地事实（路径、命名、结构）保持更新，但决策本身不改写。
- **`rejected/`** —— 考虑过并否决。当它的理由能阻止后来者重犯时保留；失去这个作用就删除。

文件名日期是主题首次提出的日期。

文件之间的引用一律用相对 Markdown 链接，不用裸文字或编号，这样可检查、可随文件移动而存活。**没有集中索引文件**：生命周期目录本身就是清单——浏览或搜索即可。

## 何时写

当一条决策有长期影响、存在真实取舍，或未来 agent 很容易重新选错时，就在做出决策的同一改动里写下它。不要为项目事实（→ `system/`）、必须/禁止的约束（→ `.pi/rules/`）、操作步骤（→ skills）写决策记录。

写之前先搜现有树：已拥有该决策的文件更新而不新建。一个文件绝不改写成另一个决策——用新文件取代它并双向交叉引用；只有每一条独有理由、落选方案与后果都被保留、且入站链接都修复后，才合并旧文件。

本目录的相对链接由仓库级检查门（`scripts/check_harness.py`）扫描；格式与内容自己核对。

## 文件格式

### 头部

每份文件的前三行固定为：

```markdown
# 决策：<标题>

状态：<status>
```

`状态：` 与所在目录一致：`proposed` / `implemented` / `rejected —— <一句话理由>`。理由只有被否状态才承载内容——它是读者打开被否文件要找的东西。

### 正文骨架

正文以 `## 问题` 开头——动机要能脱离方案独立成立。必选节之外可自由增删技术节。

`proposed/`：

```markdown
## 问题
## 方案
## 被否方案
## 验收标准
## 风险
```

`implemented/`：

```markdown
## 问题
## 决策
## 被否方案
## 后果
```

`## 决策` 用现在时陈述已落地的事实；`proposed` 专属的节名（`## 方案`、`## 验收标准`）不出现在 implemented 里。`rejected/` 是冻结的方案：保留提出时的分节，判决写在 `状态：` 行。

**`## 被否方案` 必写。** 每个真实落选方案一段，加粗领起，写清为何落选。没有记下被它击败的选项的决策，会招来重开争论。落选方案要记录，不许编造。

### 生命周期迁移

迁移 = 在同一个改动里改 `状态：` 并满足目标目录的骨架：`proposed/` → `implemented/` 把 `## 方案` 改写成现在时的 `## 决策`，把 `## 验收标准` 与 `## 风险` 折进 `## 后果`；`proposed/` → `rejected/` 在 `状态：` 行补理由并冻结文件。
