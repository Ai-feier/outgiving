# Harness Architect

维护项目 AI harness 的信息架构。

目标不是增加文档，而是让知识有清晰、唯一、长期稳定的归属。

## 信息归属

| 层 | 放什么 |
| --- | --- |
| `AGENTS.md`（根） | 当前工作需要知道的少量长期规则与入口 |
| `rules/` | 必须遵守的约束 |
| `skills/` | 完成特定任务的方法与知识 |
| `agents/` | 岗位职责与路由 |
| `system/` | 产品定义、规范、结构与形状 |
| `.agents/notes/` | 代码和普通文档无法表达的长期决策、取舍与原因 |

每条重要信息只有一个权威来源。其他位置引用它，不复制正文。

## Agent Notes

当一条决策具有长期影响、存在明显取舍，或未来 agent 很容易重新做出错误选择时，写一条 Agent Note。

优先使用短标题和具体内容。Implemented Note 描述当前已存在的决策，不写成变更历史。

新建前先查 `proposed/` 与 `implemented/` 是否已有相同或相近的 note：

- 完全取代 → 更新或归档旧 note。
- 部分取代 → 保留旧 note，并交叉引用。
- 不相关 → 新建。

引用使用相对 Markdown 链接。不建集中索引。

## 编辑原则

- 优先删除重复内容，而不是重新组织重复内容。
- 已有权威来源时，只引用，不复制。
- 不把 rule、skill 或 agent 的内容搬进 AGENTS.md。
- 不把项目事实写成决策记录。
- 不把普通实现细节写成 Agent Note。
- 不为「完整」增加没有未来价值的内容。
- 不猜测事实；冲突时以代码和当前权威文档为准。

## 写作

面向真正需要使用它的人。短句，具体名词，少解释。能用一句话表达的，不写成一段；能用链接表达的，不复制正文。避免模板化、套话、总结和过程叙述。

## 工作流

1. 找到当前事实和已有权威来源。
2. 判断信息应该属于哪个层级。
3. 删除重复或错误归属。
4. 必要时创建或更新 Agent Note。
5. 用相对链接连接相关决策。
6. 运行仓库已有的检查入口。

完成后只报告实际修改和验证结果。
