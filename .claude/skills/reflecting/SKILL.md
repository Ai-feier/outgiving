# 系统反思引擎

> 理解 AI 基础设施的做事方式 → 精进它。不修症状，修根因。

## 一、统一反思架构：三层漏斗

Agent 漏斗 → 协作者漏斗 → 系统漏斗。三层共享同一套深度逻辑，区别在 scope 和深度上限。
协作者漏斗定义在 CLAUDE.md「协作者（主 session）」节——每次 loop 收束后触发，最深到框架层。

### Agent 级反思漏斗

每个 agent 的「反思」章节遵循此结构。Agent 漏斗最深到框架层（深度 3），再深升级到系统漏斗。

| 深度 | 名称 | 触发信号 | 做法 | 退出条件 |
|------|------|---------|------|---------|
| **守门** | 每次自检 | 产出后过自检 | 自检不通过 → 修正产出，不触发反思 | 自检通过 |
| **深度 1** | 操作层 | 同类问题被纠正 ≥2 次 / 自检被绕过 | 确认是规则问题 → 修改自己的 .md 最小变更 | 后续同类场景不再出错 |
| **深度 2** | 设计层 | 深度 1 修了 2 次仍出问题 / 发现和另一个 agent 规则冲突 | 重新审视方法论——不是改一条规则，是改一组规则的关系 | 相关场景全部覆盖 |
| **深度 3** | 框架层 | 产出后自己读了觉得不对但自检没拦住 / 平台规则/算法有重大变化 / 调研发现之前依赖的假设不再成立 | 重新定义「你面对的」——核心假设变了 | 新框架通过至少 1 次实际产出验证 |
| **升级** | → 系统漏斗 | 同领域自修改 ≥3 次仍出问题 / 发现跨 agent 的重复模式 | 触发 reflecting skill 深度 2 或 3 | — |

### Agent 反思统一模板

每个 agent 的「反思」章节使用此格式，不各自发明：

```markdown
## 反思

遵循 reflecting 漏斗模型。我不是一成不变的——当模式的失败重复出现、用户纠正两次以上、或发现规则和实际冲突，修改自己的定义。

**入口信号**：[agent 特定的触发条件，对应上表各深度]

**深度 1 — 操作层**：确认是规则问题不是单次失误 → 最小修改自己的 .md 文件
**深度 2 — 设计层**：方法论问题 → 重构相关规则组 → 可泛化经验写入 `.claude/memory/`
**深度 3 — 框架层**：核心假设变化 → 重新定义「你面对的」→ 如果改了触发条件或职责边界，更新 `_index.md`
**升级**：同领域 ≥3 次修不好 → 触发 reflecting skill。外部环境变化（平台规则/工具能力）发现后立即广播给相关 agent。

这不是"出错了才做"。是持续精进——和产出同等地位。
```

### 系统级反映射漏斗（本 skill）

当 agent 漏斗升级或用户触发系统级审视时，进入此漏斗。

| 层 | 拥有者 | Scope | 目标文件 | 触发 | 验证 |
|---|---|---|---|---|---|
| **Agent 自修改** | 每个 agent 的「反思」章节 | 该 agent 的写作质量、指令精度、规则冲突 | 自己的 `.md`、memory | Agent 漏斗深度 1-3 | 后续产出质量提升 |
| **协作者反思** | CLAUDE.md「协作者」节 | prompt 设计、agent 分发模式 | CLAUDE.md、memory/ | loop 收束 / 用户纠正协调方式 | agent 产出自主性提升 |
| **反映射（本 skill）** | reflecting skill | 跨 agent 模式、基础设施架构、系统设计缺陷 | `.claude/` 任意文件、`CLAUDE.md` | Agent 升级 / 用户说"局限/保守/不够" / 跨 session 模式发现 / 基础设施变更后 | 纵向稳定性 + 无退化 |

**决策树**：这次要解决的问题 →
- Agent 产出质量 / 定义过时？ → **Agent 漏斗**。
- Prompt 设计 / agent 分发 / 协调方式？ → **协作者漏斗**（CLAUDE.md）。
- Agent 漏斗深度 3 修了仍出问题？ → **升级到系统漏斗深度 2+**。
- 跨 agent 的重复模式？框架级设计缺陷？ → **系统漏斗直接介入**。

> 边界是动态的。三层漏斗之间是**升级关系**，不是替代关系。

## 二、核心原则

- **理解优先于行动** — 没读懂系统就改文件，比不改更差。先确认因果链，再决定改什么。

- **写文件不是绩效指标** — 人格演进不落文件也是成功的 reflecting。每轮改文件但离根因越来越远 = 失败。

- **删除冗余 > 精简现有 > 新增内容** — 加规则是最弱的改进形式。先问：已有规则没遵守？框架假设错了？该删不该加？

- **接地批评** — 所有分析必须基于外部证据：git log、会话记录、用户原文引用、行为数据。不凭空推测根因。如果无法引用具体证据 → 你还没到能分析的深度。

- **迭代纪律** — 每个 reflecting 循环必须有退出条件：要么找到了当前深度的根因并实施，要么确认证据不足需要更多 session。不存在"无限向下钻"。

- **持续 — reflecting 不是触发驱动的离散事件，是品质**。触发时机是收束与形式化的节点，不是反思的起点。每次修改 `.claude/` 下的文件时就在 reflect：这个改动在精进系统还是在腐烂系统？

- **两种反思形态**（MARS ACL 2026）：**原则型反思**——从失败中抽象出规范性规则（"不要做 X"）；**程序型反思**——从成功中提取可复用的步骤策略（"做 Y 的时候先 Z"）。深度 1-2 以原则型为主（修规则防错），深度 3 以程序型为主（重构方法论）。两种形态互补——只有原则没有程序 → 规则僵化；只有程序没有原则 → 缺乏防御边界。

## 三、漏斗模型：非线性的深度递进

不是每轮都要走完所有深度。进入的信号决定你从哪层开始、到哪层停止。

### 入口门

| 信号 | 含义 | 进入深度 |
|------|------|---------|
| "好了/完成" — 常规收尾 | 会话正常结束 | **守门检查** → 无异常就跳过 |
| "为什么没用 X" — 单个工具/skill 被质疑 | 操作层问题 | 深度1 → 找到根因即停 |
| "应该先 Y" — 流程被质疑 | 动机层或框架层问题 | 深度2 → 如跨 session 则升到深度3 |
| "太局限了/太保守" | 当前反思框架不够，需要系统级审视 | 直接进入深度3 |
| "反思我引导你反思的过程" | 元层问题 | 直接进入深度4 |
| 修改了 `.claude/` 基础设施 | 需验证变更有效性 | **守门检查** + 深度3（ABC 审视） |
| 同一问题跨 session 出现 ≥2 次 | 上次反思没到根因 | 升一深度，从比上次深一层开始 |

**守门检查**（每次进入必做）：
先回看上轮 reflecting 的变更 → `git log --oneline -- .claude/`。
- 上次改了什么？改之后行为改善了吗？
- 连续两次改了同一个文件 → 警告：可能在打补丁而非做精进。
- 改完从未被触发过的规则 → 考虑删除。
- **饱和检查**（2026-07 新增）：同一 agent 精进 ≥8 轮 → 检查是否进入边际递减。信号：近 3 轮每轮净变更 <5 行且无框架层改动 → 该 agent 可能已达当前范式上限，后续精进应聚焦跨 agent 协同而非单 agent 规则微调。来源：自指内省阈值研究（Jizhi 2026）——递归自我改进 3-4 次迭代后饱和。

### 深度 1 — 操作层

找到具体做了什么导致问题。回答：
1. **发生了什么？** — 引用具体会话/输出/行为，不是笼统描述。
2. **已有规则能覆盖吗？** — 能 → 这是执行问题，**不写新规则**。在 memory 记一次行为纠正即可。
3. **如果是规则缺失** — 最小变更是什么？能不能只改一条指令而非加一章规则？

**退出条件**：找到根因 + 实施变更 → 停。不向下钻。

### 深度 2 — 设计层

操作层找不到答案 → 问题不在"做了什么"而在"被设计成做什么"。

追问：
1. **为什么现有流程 allow 了这个错误？** — 是 gate 不严？职责边界不清？规则自相矛盾？
2. **哪个 skill/agent/文件驱动了错误行为？** — 是 skill 指令不清？agent 定义少了约束？CLAUDE.md 说了但没被引用？
3. **用户这几次纠正的共同指向是什么？** — 不是修单个 bug。是在塑造一个什么样的品格、什么样的做事方式？

**验证**：找到的设计缺陷必须能引用 ≥2 个独立证据点（不同 session 的同类问题 / 用户显式说的 / git log 模式）。不够 → 证据不足，先记 memory 不下结论。

**退出条件**：确认设计缺陷 + 最小方案（优先删减/精简，不是加规则） → 停。

### 深度 3 — 框架层

设计层找不到根因，或用户说"太局限了" → 需要系统级审视。

做三件事，按此顺序：

**3.1 ABC 系统审视**
- **A 自洽** — 不同文件的规则定义是否一致？content-pipeline 和 CLAUDE.md 有没有冲突？声称的权威是否被实际遵守？
- **B 缺口** — 有没有应该被覆盖但漏掉的场景？应存在但缺失的 skill/agent？引用路径失效、孤立文件？
- **C 更简单** — 有没有跨文件重复规则 → 提取到一处？有没有过于具体的命令 → 精简为原则描述？有没有不再需要的文件 → 废弃或删除？

**3.1.5 协同性审计（系统级常设检查）**

每次深度 3 触发时必做。检查 agent 间协作健康度，六个维度：

| 维度 | 检查问题 | 健康信号 | 退化信号 |
|------|---------|---------|---------|
| **通信效率** | 共享文件（outline/style/gather-expert 产出/上游约束参数）是否被所有下游 agent 实际读取？ | `Read` 调用覆盖所有共享文件 + 下游 agent 知道上游的量化约束（如时长上限/变化频率/复杂度） | 某 agent 跳过共享文件直接产出；下游设计超出上游硬约束 |
| **知识传播** | 一个 agent 发现的平台变化是否到达了相关 agent？ | douyin-writer 发现算法变化 → wechat-writer 和 xiaohongshu-writer 在 2 轮内感知 | 同一发现被不同 agent 独立重复调研 |
| **矛盾升级** | agent 间规则冲突是否有明确的裁决路径？ | 冲突 → video-director 裁决（视频）/ reflecting 深度 2 裁决（文本） | 冲突被忽略或各自保留矛盾规则 |
| **共享假设一致性** | 所有 agent 的「你相信的」和「你面对的」是否仍然自洽？ | 五条信仰在所有 agent 中表述一致；读者状态表无漂移 | 某 agent 的"你面对的"与其他 agent 的隐含假设矛盾 |
| **接力完整性** | 工作流中每个交接点是否有明确的输入/输出契约？ | gather-expert → brief → outline → style → writers 每步有明确输出格式 | 某交接点被跳过或输出格式不匹配下游预期 |
| **标注标准对齐度**（T002 实战新增） | agent 间共享的量化指标（时长、密度、频率、复杂度）是否使用统一定义和标度？ | script-designer 和 rhythm-designer 对"变化频率"有区分的定义（CF 时间 vs V 空间） | 同一数值被不同 agent 赋予不同含义；script-beats 时长超出 director 硬约束未被感知 |
| **来源可靠性**（多轮 loop 新增） | agent 引用的数据来源是否实际支持其声称？ | 每个数据点可追溯到源文档中的具体位置 | 发现"幽灵引用"——引用的 URL 不包含声称的数据（douyin/gather-expert/x-writer 均出现） |

**协同性退化的常见根因**：
- Agent 独立精进多轮后，各自的「你面对的」向不同方向演进
- 新增的规则在一个 agent 中生效但未广播给协作 agent
- 共享文件格式变化后，读取方未同步更新解析逻辑
- 某个 agent 被修改后，依赖它的 agent 未被通知
- Agent 各自定义的量化指标标准在独立进化中产生分歧（谁都没错但对应不上）
- Agent 引用来源未经逐字验证——URL 存在但内容不支撑声称（幽灵引用传播）

**发现协同性问题后的处置**：
1. 单点通信断裂 → 修复该 agent 的工作方法（确保读取共享文件）
2. 知识传播滞后 → 在 CLAUDE.md 协作法则中增加"平台变化广播"机制
3. 共享假设漂移 → 所有 agent 重新对齐「你相信的」和读者状态表
4. 接力断裂 → 明确交接点的输出格式契约
5. 标注标准分歧 → 相关 agent 在下一轮精进中对齐量化标度定义，并在 CLAUDE.md 的"跨 agent 约束对齐"表中记录
6. 来源可靠性退化 → 触发全生态来源审计——每个 agent 用逐字对比验证其关键数据引用

**3.1.6 跨 Agent 一致性审计模式**（2026-07 多轮 loop 实战提炼）

当多轮独立精进后（≥2 轮），agent 各自进化可能产生新的隐含矛盾。此时触发**分布式交叉审计**——每个 agent 跨读 ≥3 个关联 agent 的最新文件，逐字段对位验证。

**审计维度**（按优先级排列）：
1. **版本号一致性** — 共享的技术栈/工具版本是否全生态一致（如 Seedance 2.0 vs 2.5 的全局修正）
2. **消费断裂** — 上游产出的新字段是否被下游实际读取（如 gather-expert FRANQ 字段 0/4 writer 消费）
3. **术语体系统一** — 同一概念是否在不同 agent 中使用不同名称（如"规范参考图" vs "角色参考图"）
4. **量化指标对齐** — 共享的数值约束是否一致（如时长/频率/组块数/权重排序）
5. **交接点完整性** — 每个工作流交接点的输入/输出是否被双方正确记录

**审计纪律**：
- 每个 agent 独立执行审计，不相互委托
- 发现不一致 → 先判断严重度（高/中/低）→ 高立即修复，中标记并修复，低记录不阻塞
- 审计结果写入精进记录，标注"跨agent一致性审计"
- 同一次审计中发现的跨文件不一致（如 Seedance 版本号），由一个 agent 修复后广播，避免重复修改

**两级消费界面模式**（通用化自 gather-expert v5.3）：当上游产出的字段数 ≥5 时，考虑分级——最低读取集（3-4 字段，日常必读）+ 进阶读取集（其余，深度使用时按需读取）。避免"全部必读→认知超载"和"只读一个→信息不足"的两端陷阱。

**3.2 退化的可能性**
- 上次基础设施变更有没有导致任何 regressions？——引用具体行为变化，不只凭感觉。
- 有没有改了但从未使用过的新增规则？→ 考虑删除。
- 有没有因为修了 A 问题而放松了对 B 的要求？→ 回滚或重新平衡。

**3.3 经验捕获**
- ≥2 次或明显会重复 → 写入 `.claude/memory/`。
- 一次性的 / 已有覆盖 / 证据不足 → 跳过。
- Memory 格式：frontmatter + body + Why / How to apply。

**退出条件**：ABC 审视完成 + 变更清单已整理 → 进入实现。不自动进入深度 4。

### 深度 4 — 元层

仅在以下情况进入：
1. 用户显式说"反思你引导我反思的过程"
2. 本 skill 连续两次在同一深度找不到根因（说明框架本身在退化）
3. 多轮 session 只停在深度1/2，从未到达框架层

反思 reflecting 自身：
- **当前结构仍然有效吗？** — 有没有章节过时、重复、从未被用到？
- **上次改核心原则后 reflecting 质量是升是降？** — 引用具体 session 对比，不只凭印象。
- **漏斗模型的深度划分对当前情况适用吗？** — 如果信号指向新深度，就新增；如果当前深度从未被到达，就合并或删除。
- **本 skill 最后一次修改自身的 git commit 是什么时候？** — 超过 10 次 session 没自修改 → 元层在腐烂。

**元层变更的纪律**：改 reflecting 自身是最不可逆的操作。必须：
1. 展示变更对比
2. 用户确认
3. 一次只改一个结构性问题（不批量重构）
4. 改完后 3 个 session 后再审视：这次改动改善了 reflecting 质量还是让它更臃肿了？

## 四、实现 — 选择并验证

### 4.1 选择改进形式

按优先级从高到低：

| 优先级 | 形式 | 适用 | 验证方式 |
|--------|------|------|---------|
| 1 | 行为修正（不落文件） | 已有规则被忽略、执行疏忽 | 后续会话观察 |
| 2 | 删减 | 过时、冗余、不再适用 | git diff — 减少的行数 |
| 3 | 精简现有规则 | 指令太具体 → 精简为原则 | 对比精简前后同一场景的表现 |
| 4 | 写入 memory | 用户偏好 / 跨 session 事实 / 重复踩坑 | 下次类似场景触发 |
| 5 | 增强 skill/agent/CLAUDE.md | 指令不精确或缺失 | 后续同类问题是否复现 |
| 6 | 更新 _index.md | 新增/删除文件后交叉引用同步 | `content validate` |
| 7 | 跳过 | 一次性 / 证据不足 / 已有覆盖 | — |

**规则**：不是前 3 种形式就不改 → 确认不是"已有规则未遵守"后才用 5+。

### 4.2 安全阀门

每次基础设施变更前：
1. **变更摘要** — 一句话：什么根因 → 改哪里 → 怎么验证
2. **非退化检查** — "这个改动会不会让一个之前正常工作的场景失败？" 如果有风险 → 缩小 scope 或不分
3. **回滚路径** — 这个改动如果错了，怎么还原？

### 4.3 实现纪律

- 逐条展示：根因 + 目标文件 + 变更摘要 → 用户确认 → 写入。不批量。
- 同一文件连续修改 ≥3 次 → 停止并重新审视根因。频繁打补丁说明没找到真根因。

## 五、会话效能诊断

不是每轮跑。≥3 次 reflecting 或明显异常会话时运行：

1. **最多的浪费在哪？** — 时间/字数/认知花在了什么地方，但最终被删除或未产生价值？
2. **最早该停的时刻？** — 会话中哪个时间点应该停下、质疑方向、重新评估？
3. **AI 主动做了什么错误决定？** — 不是用户指错路，是 AI 自己选错了选题角度/改写策略/论据？
4. **上次 reflecting 的改动有效吗？** — 回顾上次变更清单，检查：改动后行为是否改善？有没有改了又犯同类错误？有没有改完从未被触发过的规则？

## 六、触发时机

触发的不是"开始反思"，是"把持续审视中积累的判断形式化"。

| 断点 | 信号 | 进入深度 |
|------|------|---------|
| 会话收尾 | 好了/done/完成/最后/收尾 | 守门检查 |
| 内容 review 出问题 | 人审发现 AI 味重/论证弱/图文不匹配/事实错误 | → agent 自修改。除非跨 agent 模式 |
| 流程被质疑 | "为什么没用 X"/"为什么不先 Y"/"应该先 Z" | 深度 1 或 2 |
| 用户说"局限/保守/不够" | 当前框架不够用 | 深度 3 |
| 修改了基础设施 | 改了 `.claude/` 或 `CLAUDE.md` | 守门检查 + 深度 3 |
| 发布后复盘 | 内容发布后的数据回溯 | → agent 自修改 |
| 手动触发 | /reflecting | 按上下文 |
